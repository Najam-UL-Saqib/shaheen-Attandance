Shaheen Timetable v2 Plan

The client watched the demo and came back with nine requirements. Some are quick. Two of them change the core rule the timetable is built on — that one class, and one teacher, do exactly one thing per period. This is the read on all nine, what each one touches, and the order to build them in.

Date 4 Sep 2026 Baseline 29 teachers · 24 sections · 708 weekly periods Status awaiting decisions

01 The shape of the work

Five of the nine are additive and can land quickly — the day-view reassignment helpers, the emergency relaxation of the 3-consecutive rule, showing teacher names in the report, tests & function days. They need decisions, not architecture.

The other two — combined classes (one teacher, both sections of Class 9 for Computer) and elective splits (in one section, some pupils do Biology while others do Computer, same period, two teachers) — both need a period to hold more than one lesson. That is exactly what the two database rules added last week forbid. Those rules don't get deleted; they get a defined exception.

Underneath all of it is the frontend. The data model is sound; the screens assume you already know how a timetable system thinks. That's the real reason the demo felt hard to follow, and it gets its own pass.

What the new requirements break

Migration 20260904080901 added unique (teacher_id, day, period) and the app already had unique (section_id, day, period). Combined classes violate the first; elective splits violate the second. Both become conditional: allowed when the lessons share a teaching_group (combined) or an elective_block (split). Reports, auto-generate, and the timetable grid all read those constraints today, so all three change with them.

02 Where the system stands

Everything below already works and is tested (16 unit, 23 end-to-end, a full data-integrity audit). The plan builds on it, not over it.

Data model

  • subjects, classes (1–12), sections (A/B) + class teacher
  • class_subjects — curriculum per class
  • teacher_allocations + _subjects — weekly load, split by subject
  • timetable_slots — the weekly grid
  • timetable_day_overrides — per-date changes (is_game)
  • game_period_assignments, school_settings

Screens

  • Setup — Subjects, Classes & Sections, Teachers, Rooms
  • Workload Allocation — who teaches what, how much
  • Timetable — build the weekly grid, auto-generate
  • Day View — substitute / free / game, per date
  • Reports — Class×Subject, Teacher×Class
  • Settings — schedule shape, one school-wide break, theme

Rules enforced

  • One lesson per section per period (DB)
  • One lesson per teacher per period (DB, new)
  • ≤ 3 consecutive periods — configurable, hard block
  • Timetable periods ≤ the teacher's allocation
  • Teacher must be allocated to the section

03 The nine requirements

R1

Combine two sections under one teacher

Class 9 has A and B. For Computer, one teacher takes both together in one room, one period. It should count as delivered for both sections and as a single period of that teacher's week.

R2

Allow >3 consecutive periods in Day View, for emergencies

The weekly timetable still refuses it. But when an admin is covering an absence on the day, they can push a teacher past three in a row — the cell just turns a warning colour.

additive S touches day-view save · cell colour
R3

Put the teacher's name back in the report

Class×Subject was just trimmed to bare numbers. The client wants the teacher for each class/subject visible again. Full names make the table wide; short names or initials keep it on one screen. A client call.

decision name format S touches reports Table A
R4

Elective splits — Biology / Computer in the same period

In Pakistan a section isn't uniform: some pupils choose Biology, others Computer. Both run at once, different teachers, different rooms. The section's period holds two parallel lessons, and a pupil's timetable depends on their choice. We track this at the group level, not per pupil.

breaks section/period unique decision XL touches schema · curriculum · allocation · timetable · reports · day-view
R5

Cover a teacher who leaves mid-day

A teacher takes periods 1–2 then leaves for the day. One action marks them away from period 3, lists every lesson of theirs still to come, and lets the admin reassign each.

additive M touches day-view · (optional) absence record
R6

Show who's actually free when reassigning

When covering a gap, the picker shows teachers who (a) aren't teaching that period and (b) already teach that class/section. A "show all available teachers" button widens it to anyone free. Busy teachers don't appear as options.

additive M touches day-view substitute picker
R7

Breaks per group of classes, not one for the school

Today there's a single "break after period N" for everyone. Instead: create a named break, add the classes it covers, set its timing. Primary and senior sections can break at different points. The grid and auto-generate honour each section's own break.

decision per class or per section L touches schema · settings · timetable grid · day-view grid · auto-gen
R8

Test periods & school-function days

In Day View, mark a range of a class's periods as Test, optionally with an invigilator (assigning is optional; over-3-consecutive is a warning, not a block). Separately, mark whole classes as tied up in a function so their periods clear.

decision scope & range rules L touches override kind · day-view · range UI
R9

Make the whole thing understandable

The demo was hard to follow. Ten flat menu items, screens that assume you know the model, system words ("allocation", "slot", "override"), no sense of what to do first. Reorder around the real workflow, give the dashboard a job, plain language, guided setup, clear empty states, simpler cell dialogs.

decision how far to go L–XL touches navigation · dashboard · every screen's copy · onboarding

04 The one model change everything else needs

R1 and R4 are the same shape at bottom: a period can carry more than one lesson, and a lesson can serve more than one section. A single concept covers both.

Teaching group. A named set of (section, subject) pairs taught as one unit. Two kinds:

  • Combined — {9A·Computer, 9B·Computer}, one teacher, one room, one slot in the week. Both sections show Computer at that time; the teacher's load counts it once.
  • Elective block — {9A·Biology, 9A·Computer}, same section, same period, two teachers, two rooms. A section can only run its subjects in parallel inside a declared block.

The two unique constraints keep protecting the normal case and gain one carve-out each: a teacher may hold two slots at one time only if they're the same combined group; a section may hold two slots at one time only if they're the same elective block. Everything that reads the grid today — conflict checks, auto-generate, both report tables — learns the group concept once, here.

06 Decisions needed before Phase 1

  1. Combined class — does it count once or twice against the teacher's weekly load? One room, one lesson, so once is the natural answer. Confirm, and confirm it still counts toward each section's own subject total. R1
  2. Elective — do we ever need to know which pupil is in which group? The system has no pupil records today. Assumption: we track "the section splits into these subjects" and nothing finer. If individual pupil timetables are needed, that's a much bigger piece. R4
  3. Which subjects are electives, in which classes? e.g. Biology ↔ Computer in Classes 9–10. Needed to seed the elective blocks and adjust the curriculum screen. R4
  4. Report — full teacher names, initials, or a "show teachers" toggle? Full names bring back the horizontal scroll the last change removed. Initials or surname-only keep it on one page; the toggle gives both. R3
  5. Breaks — attached to a class (both sections together) or to a section? And can one section have two breaks in a day (e.g. a short break and a lunch)? R7
  6. Test periods — still tied to a subject, or just "Test"? i.e. does "9-A period 3 is a Maths test" matter, or only "9-A period 3 is a test". Also: is picking a period range (3–5) enough, or do tests need finer control? R8
  7. Function days — whole class only, or specific sections? Whole day or a range? Decides whether "in a function" is a class-level or section-level mark and whether it takes a period range. R8
  8. R9 — how far does the usability pass go for the next demo? A light pass (nav order, dashboard, language, empty states) is ~1 week. A guided setup flow and rebuilt dialogs is more. Which one does the next demo need? R9

07 Recommendation for the next demo

Lead with Phase 1 — it's fast, it directly answers four of the client's points, and it makes Day View feel solid. Show a working combined class from Phase 2 if the schedule allows. Hold electives and the full usability rebuild for the demo after; they're where the risk is.
