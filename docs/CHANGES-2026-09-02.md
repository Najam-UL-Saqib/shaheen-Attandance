## 2. Hard-coded settings moved to the Settings tab

### New setting: **Max consecutive periods per teacher**

- Stored in `school_settings.max_consecutive_periods` (default `3`).
- Migration: **`supabase/migrations/20260902190944_configurable_consecutive_limit.sql`** — must be applied (see §4).
- Edited on **Settings → Weekly schedule**.
- Consumed by:
  - `src/routes/timetable.tsx` — cell save validation, conflict list, and the **Auto-generate** algorithm
  - `src/routes/day-view.tsx` — substitution save validation and the "consecutive periods" cell highlighting
- All previously hard-coded `3` / `4` strings now interpolate the live value.
- Falls back to `3` (the `MAX_CONSECUTIVE_TEACHING_PERIODS` constant) while settings load or if the migration has not been applied yet.

### Already configurable (unchanged)

`working_days`, `periods_per_day`, `break_after_period` — already on the Settings tab. The fallback
constants (`DEFAULT_WORKING_DAYS`, `DEFAULT_PERIODS_PER_DAY`, `DEFAULT_BREAK_AFTER_PERIOD`) now live
together in `src/lib/schedule.ts` instead of being inline literals.

### Not settings (left as-is)

Theme colours (already user-configurable via `Settings → Appearance`, stored per-browser),
day names, UI spacing / colours.

### Bugs fixed while wiring the new setting

`src/routes/settings.tsx` mishandled the `["settings"]` query lifecycle two ways, both able to
**silently persist wrong values** for `working_days` / `periods_per_day` / `break_after_period` /
`max_consecutive_periods` (one `save()` writes all four):

1. It re-seeded every field from `data` on **every** `data` change — a refetch mid-edit (window
   focus, post-save invalidation) reverted unsaved edits. Now seeded once via a `seeded` ref.
2. Nothing stopped a `save()` before the row had loaded, so it wrote the `useState` defaults
   (`break_after_period: 0`, etc.). Now the Save buttons are `disabled={!data}` and `save()` early-returns
   when `data` is undefined.

Both caught by the Playwright settings-persistence test.

## 3. Reports — Table A rework

### Table A — *Class/Section × Subject* (final layout)

- **One number per cell** — the weekly periods assigned for that subject (teacher name and the
  `allocated / used` pair moved to a hover tooltip). A red number means the timetable count ≠ the
  allocation.
- **First column** — `<class> – <section>` with the **class teacher name inline** on the same line
  (small, no label).
- **Games** column — count of game / PT periods for the section.
- **Total** column — a single number: the section's assigned subject periods (games excluded).
- Compact: `table-fixed`, short horizontal subject headers (`Eng`, `Gen Sci`, … full name on hover),
  tight one-line rows — no horizontal scroll, the whole 24-row table fits one screen.

### Export PDF

- **Export PDF** button in the Reports header → `window.print()`.
- `@media print` rules in `src/styles.css` drop the sidebar, tabs, and the button, expand the table
  to the page, and force `A4 landscape`. Prints whichever tab is open. Elements tagged `.no-print`
  are hidden; the report card is tagged `.print-area`.

### Table B — *Teacher × Class/Section*

- Same compact single-number treatment: each cell is the periods the teacher is assigned in that
  class/section (allocated vs timetable on hover, red on mismatch). Compact `1A`…`12B` headers,
  `table-fixed`, one-line rows — the whole 29-teacher matrix fits one screen / one landscape page.
- **Total** — the teacher's whole-week workload as a single number.

### Why some cells are still `—` (not a bug)

- **Table A** `—` = the subject is **not in that class's curriculum** (e.g. grade 3 has no Physics).
  There is no teacher or period to show. Every cell that *should* have data shows `N / N`.
- **Table B** `—` = that teacher is **not assigned to that section**. A real teacher only teaches
  5–6 sections, so the teacher×section grid is inherently ~75% empty. It cannot be filled without a
  teacher covering all 24 sections (100+ periods/week), which is impossible. Fewer teachers make it
  denser but never full.
